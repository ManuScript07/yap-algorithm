# Yap Algorithm

Внутренний рекомендательный сервис YapChat: Go, PostgreSQL/pgvector и локальная CPU-модель multilingual E5. Проект находится в разработке.

## Текущий статус

| Контур | Что работает |
|---|---|
| Настоящая Supabase YapChat | Текст и фото, закрытый Storage, геометки, лайки, комментарии/ответы, репосты/цитаты, подписки, жалобы, персонализация и страницы «Для вас»/«Друзья»/«Рядом» через Supabase |
| Изолированный прототип | Несколько источников кандидатов, профили интересов из взаимодействий, гибридное ранжирование, разнообразие, тестовый симулятор и исследовательское обучение |

Асинхронная персонализация, три серверные ленты, жизненный цикл фото и социальные взаимодействия работают в локальной Supabase. Inbox, клиентский интерфейс и оценка/обучение моделей остаются следующими этапами. Облачное развёртывание пока не проверялось.

Клиент обращается к Supabase Auth/RPC и Storage. Внутренний `cmd/worker` забирает задания из той же PostgreSQL, вызывает модель и записывает производные векторы обратно. Клиентский HTTP API для этого worker отсутствует. Шлюзом и источником истины остаётся Supabase.

## Архитектура

- `internal/domain` — ограничения предметной области, векторы и ошибки.
- `internal/application` — сценарии обработки и интерфейсы зависимостей.
- `internal/adapters/postgres` — закрытый SQL-контракт, пул и проверка прав.
- `internal/model` — HTTP-адаптер модели с проверкой пространства эмбеддингов.
- `internal/ranking` — признаки, базовый score и разнообразие.
- `cmd/worker` — сборка зависимостей, параллельность, остановка и очистка.
- `cmd/media-worker`, `internal/adapters/photo`, `internal/adapters/storage` — отдельная ограниченная обработка изображений и физическая очистка через Storage API.
- `internal/api`, `internal/store`, `internal/worker`, `cmd/yap-algorithm` — сохраняемый изолированный прототип.

Публикация и задание записываются одной транзакцией. Работники используют `SKIP LOCKED`, ограниченный срок владения и повторные попытки. Перед сохранением вектора повторно проверяются версия и состояние поста. Сервисная роль имеет права только на внутренние функции, а не на изменение публикаций или профилей.

Для ранжирования используются архитектурные идеи поэтапного конвейера [x-algorithm](https://github.com/xai-org/x-algorithm): поиск кандидатов, фильтрация, оценка, разнообразие и итоговые проверки доступа. Собственные модели и веса X здесь не используются. Текущий гибридный score — проверяемая исходная модель; его коэффициенты ещё требуют продуктовой валидации.

## Зависимости и модель

Нужны Go 1.27.3+, Python 3.12 и Docker для локальных проверок. Минимальная Go закреплена с учётом исправлений стандартной библиотеки; при включённом автоматическом выборе toolchain нужная версия скачивается в локальный кэш проекта. Зависимости закреплены в `go.mod`, `go.sum` и `ml/requirements.lock`. Масштабирование изображений использует официальную `golang.org/x/image` v0.47.0.

```powershell
uv venv --python 3.12 .venv
uv pip sync --python .venv/Scripts/python.exe ml/requirements.lock
```

Используется `intfloat/multilingual-e5-small`, ревизия `614241f622f53c4eeff9890bdc4f31cfecc418b3`, ONNX int8, 384 измерения. При первом запуске скачиваются открытые веса; они не включены в репозиторий. GPU и платный модельный API не требуются.

## Локальная Supabase YapChat

Нужна работающая локальная Supabase основного приложения на портах API 54321 / PostgreSQL 54322 с каноническими миграциями `20261104195702_feed_recommendation_pipeline.sql`, `20261104213317_personalized_feed.sql`, `20261104225631_feed_media_pipeline.sql`, `20261105120329_feed_media_capacity.sql`, `20261105143118_feed_social_interactions.sql`, `20261105174213_feed_author_subscriptions.sql`, `20261105183530_asynchronous_recommendation_preparation.sql`, `20261105184444_nearby_post_feed.sql`, `20261105221243_optimize_bounded_feed_reads.sql`, `20261105235213_feed_feedback_history.sql` и `20261106143352_optimize_followed_author_reads.sql` из репозитория YapChat. Они зависят от существующих проверок и таблиц приложения. Worker не применяет миграции при запуске.

Для исследовательского экспорта дополнительно нужна миграция `20261111135435_recommendation_dataset_capture.sql` из того же репозитория.

```powershell
$appRoot = 'D:/path/to/Yap_chat'
./scripts/supabase-local.ps1 -Action setup -AppRoot $appRoot
```

Настройка создаёт ограниченный локальный логин и случайный пароль. Настройки остаются в игнорируемом `.local/`. Ключ Supabase `service_role` самому worker не нужен.

В отдельных терминалах:

```powershell
./scripts/local.ps1 -Action model
# После сообщения ready, в другом терминале:
./scripts/supabase-local.ps1 -Action worker
# Обработать доступную очередь и завершиться:
./scripts/supabase-local.ps1 -Action worker -Once
# После устранения ошибки модели можно переотправить исчерпавшие попытки:
./scripts/supabase-local.ps1 -Action worker -RetryFailed
# Восстановить недостающие векторы: один ограниченный диапазон UUID, максимум 500 постов.
./scripts/supabase-local.ps1 -Action worker -EnqueueBackfill -BackfillLimit 500
# Продолжить с after_post из результата (если has_more=true):
./scripts/supabase-local.ps1 -Action worker -EnqueueBackfill -BackfillAfter 'UUID_КУРСОРА'
```

По умолчанию работают 2 задачи с максимум 4 SQL-соединениями. Для удалённого запуска `cmd/worker` принимает `DATABASE_URL` и внутренний `MODEL_URL`; удалённая БД требует `sslmode=verify-full`. Локальные helper-скрипты удалённые адреса не принимают. Облачное развёртывание ещё не проверено.

### Фото и геометки

```powershell
./scripts/media-local.ps1 -Action setup -AppRoot $appRoot
./scripts/media-local.ps1 -Action worker
# Обработать доступные фото и удаления, затем завершиться:
./scripts/media-local.ps1 -Action worker -Once
```

Медиа использует отдельный логин БД и JWT с ролью `yap_feed_media_worker`, ограниченной Storage RLS. Ключ `service_role` и секрет подписи JWT обработчику не передаются. Локальный setup выдаёт токен на 7 дней; для продления повторите setup и перезапустите процесс. Конфигурация остаётся в `.local/`. Для удалённого запуска нужны `MEDIA_DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` и заранее выпущенный `MEDIA_STORAGE_TOKEN` этой роли. URL Storage требует HTTPS, БД — проверенного TLS. Выпуск и ротация удалённой идентичности требуют отдельной настройки окружения; локальный helper туда не подключается.

По умолчанию работает одна медиа-задача на процесс, максимум — две. Общие SQL-слоты допускают не больше двух одновременных обработок фото между всеми процессами. Декодирование ограничено 20 мегапикселями и стороной 8192; качественное масштабирование требует отдельного бюджета памяти. На небольшом VPS начните с одной задачи и измерьте память на своём корпусе. Медиа не занимает очередь семантической индексации.

Порядок для будущего клиента через существующую Supabase-сессию:

1. `reserve_feed_photo(post_id, photo_id, bytes, MIME)` возвращает точный путь в закрытом `feed-uploads`. Сохраните UUID и исходные параметры для повторов.
2. Загрузите JPEG/PNG до 5 МиБ обычным `storage.from(bucket).upload(path, bytes, upsert: false)` с объявленным MIME. Оригинал нельзя читать, копировать, перемещать или подписывать.
3. Вызовите `confirm_feed_photo`, затем `get_feed_photo_status` с увеличивающимся интервалом опроса. До состояния `ready` публикация невозможна. Держите локальное превью; сервер проверяет декодирование, поворот EXIF и удаляет метаданные.
4. `publish_feed_post` принимает UUID черновика, текст, аудиторию, язык, упорядоченные UUID готовых фото и необязательную геометку. До трёх фото; текст может отсутствовать. Фото и геометка после публикации фиксированы, текст редактируется обычным RPC.
5. DTO поста содержит `photos` с путями очищенных JPEG и превью. Читайте через авторизованный Storage download с текущим JWT. Подписанные и публичные URL закрыты, текущие права проверяются на каждом сетевом чтении. Кэш байтов должен быть привязан к аккаунту и очищаться при потере доступа; уже скачанные байты сервер отозвать не может.

Есть `cancel_feed_draft` для отказа от загрузки. На пользователя разрешены четыре активных черновика, 48 новых резервирований за скользящий час, по 60 запросов/минуту на каждую медиа-операцию. Черновик истекает через час. Физическая очистка оригиналов, прерванных попыток и удалённых постов идёт через устойчивую очередь и Storage API; рабочий медиа-процесс должен быть запущен. После исправления сбоя `-RetryFailed` возвращает ограниченную пачку исчерпанных заданий в работу.

Общее резервирование учитывает и ещё не загруженные файлы: по умолчанию до 256 активных резервов, 120 незавершённых обработок, 512 МиБ заявленных оригиналов и 1 ГиБ оценочного временного долга. Действует первый достигнутый предел. Новые резервы также приостанавливаются при возрасте рабочей очереди больше 60 секунд или долге более 2048 готовых к очистке объектов. Счётчики изменяются транзакционно; освобождение выполняется после изменений исходных строк, чтобы массовая публикация, отмена и очистка не захватывали блокировки в обратном порядке.

При отказе в новом резерве возвращаются HTTP **429**, `code=media_capacity_exceeded` и `Retry-After` (по умолчанию 15 секунд). Повторяйте тот же запрос после задержки с небольшим случайным разбросом. Если транспорт не предоставляет заголовки, та же задержка находится в JSON-строке `details` как `retry_after_seconds`. Это отдельный код от пользовательской квоты `42901`. Подтверждение, статус, отмена и точный повтор действующего резерва работают при закрытом приёме новых загрузок. Истёкший черновик имеет `state=expired`; reserve/confirm/publish возвращают HTTP 410 `photo_reservation_expired`, после чего нужны новые UUID и загрузка. Фото опубликованного черновика, не включённые в пост, имеют статус `discarded`.

RLS проверяет MIME и доступ к пути, а дополнительный триггер проверяет фактические размер, MIME и действительность резерва при финальной записи метаданных Storage, включая запись внутренней ролью Storage. Стандартные бинарная и multipart-загрузка поддерживаются. Триггер не изменяет системные функции Storage; его совместимость следует повторно проверять медиа-тестами после обновления Supabase. Состояние очереди не является общей квотой S3: опубликованные изображения, внутренние временные версии Storage и входящий сетевой трафик требуют собственных метрик и ограничений окружения.

### Контроль медиа-очереди

```powershell
./scripts/media-local.ps1 -Action worker -Status
```

Команда выводит агрегаты без пользовательских текстов, путей и токенов: состояния/возраст очереди, долг очистки, повторы и ошибки, занятые слоты и зарезервированные соединения. Суммы и интервальные гистограммы времени ожидания/обработки накапливаются в БД, поэтому перезапуск процесса их не сбрасывает. Работающий процесс каждые 30 секунд пишет эти агрегаты, Go heap/sys, число goroutine и состояние своего пула. Это структурированные JSON-логи; доступ к внутреннему `media.queue_snapshot()` есть только у ограниченного медиа-воркера и администратора.

Каждый процесс регистрирует бюджет пула `concurrency+1`, продлевая регистрацию раз в 5 секунд; общие значения по умолчанию — два процесса и шесть соединений. После утраты регистрации процесс останавливается, а его результат не может стать готовым фото. Запускайте его под supervisor с перезапуском при ошибке. Lease задания остаётся отдельным механизмом восстановления; старые попытки пишут в отдельные пути, учтённые очередью очистки. Диагностические и административные соединения необходимо учитывать отдельно при настройке ограничения LOGIN-роли в PostgreSQL.

Настройки находятся в закрытой таблице `media.capacity`; меняет их администратор. `paused=true` прекращает новые резервы, сохраняя обработку уже принятой работы. Лимиты параллельности и ресурсов меняйте после остановки и завершения активных попыток. `temporary_bytes` — консервативная сумма оценок зарегистрированных путей очистки, включая ещё не записанные результаты попыток, а не измерение файловой системы. При аварии проверьте возраст очереди, повторные ошибки, наличие места в Storage и живые регистрации; исправьте причину и примените `-RetryFailed` при исчерпании попыток.

Геометка хранит место публикации и не зависит от видимости пользователя в поиске рядом. Точные координаты получает автор и текущие друзья с разрешением точной локации без индивидуального исключения. Остальным возвращается только `nearby=true` в пределах 50 км при собственной позиции не старше 12 часов; точного расстояния нет.

Фото без текста не отправляется в E5 и не получает выдуманный семантический вектор. Его лайки и чтение влияют на авторские/поведенческие источники. Мультимодальная семантика — отдельный будущий этап оценки моделей.

### Ручная проверка без клиента

Откройте локальную Studio на `http://127.0.0.1:54323`. Создайте отдельного тестового пользователя в Authentication и скопируйте его UUID. В SQL Editor выполните:

```sql
begin;
select set_config('request.jwt.claim.sub', 'UUID_ТЕСТОВОГО_ПОЛЬЗОВАТЕЛЯ', true);
set local role authenticated;
select public.create_feed_post(
  'f0000000-0000-4000-8000-000000000001',
  'Разрабатываю сервер на Go и PostgreSQL', 'public', 'ru'
);
commit;
```

Это локальная административная имитация идентичности, а не проверка JWT. Для настоящего Auth/PostgREST предусмотрен сквозной тест ниже. Не меняйте `auth.uid()` или claims в клиентском коде.

Пост сохраняется в `feed.posts`, задание — в `recsys.index_jobs`. После обработки проверьте в SQL Editor:

```sql
select p.id, p.version, j.attempts, j.done_at, j.last_error,
       e.post_version, e.model, extensions.vector_dims(e.embedding) as dimensions
from feed.posts p
left join recsys.index_jobs j on j.post_id = p.id
left join recsys.post_embeddings e on e.post_id = p.id
where p.id = 'f0000000-0000-4000-8000-000000000001';
```

Ожидается завершённое задание, отсутствие ошибки и вектор размерности 384 с текущей версией поста. Измените текст через `public.edit_feed_post(id, expected_version, new_text)` — версия увеличится, вектор будет пересчитан. Повтор создания с исходным UUID и параметрами не создаёт дубликат.

Для проверки персонализации создайте второго тестового пользователя и несколько постов о разных темах. Под его идентичностью вызовите `public.get_for_you_feed()`, возьмите `delivery_id` и `post.action_version` из ответа и вызовите:

```sql
select public.apply_feed_action(
  'НОВЫЙ_UUID_ДЕЙСТВИЯ', 'DELIVERY_ID_ИЗ_ВЫДАЧИ', 'like', 0
);
-- После обработки worker:
select public.get_for_you_feed();
```

Последний аргумент — фактический `action_version`, а не всегда 0. Для транспортного повтора сохраните исходный UUID и всё тело запроса. Новое намерение пользователя получает новый UUID и актуальную версию. Повтор старого запроса не отменяет более новое действие. На HTTP 409 сверяйте текущее состояние, не переигрывайте старое намерение с новой версией.

Текстовая `post.version` и `post.action_version` — разные версии. Для семантического сигнала `less_similar` используйте тот же RPC; для скрытия автора и сброса есть отдельные RPC.

## Контракт для клиента

[OpenAPI Supabase RPC](api/supabase.openapi.yaml) описывает параметры, ответы, пагинацию и ошибки. Все вызовы идут через существующую Supabase-сессию и сетевой слой приложения. Не обращайтесь к Go или закрытым таблицам из клиента.

- `get_for_you_feed` — до 30 постов, непрозрачный UUID сессии и `next_cursor`; передавайте оба поля курсора на следующей странице. Позиции могут иметь пропуски после банов, удаления или изменения текста.
- `apply_feed_action` — `like`, `unlike`, `less_similar`, `undo_less_similar`, с UUID намерения и версией состояния действий.
- `record_feed_events` — до 100 событий за запрос. Доставленный пост ещё не является показом: отправляйте impression после 1 секунды при видимости хотя бы 50%, затем cumulative dwell/open_post.
- `set_recommendation_author_hidden`, `reset_recommendation_interests` — идемпотентные операции настроек с UUID запроса. Выполняйте изменения настроек последовательно в клиентском репозитории.
- `get_recommendation_hidden_authors` — keyset-пагинация списка скрытых авторов.

Показы и действия с любой поверхности используют общий профиль: `get_feed_post` выдаёт подтверждение `direct`, персональная страница — `for_you`, `get_friends_feed` — `friends`, `get_nearby_feed` — `nearby`. Подписки добавляют явный авторский и семантический интерес, не предоставляя права друга.

`refresh.status` показывает `fresh/queued/retrying/failed`. При недоступности worker остаётся допустимая подготовленная выдача либо ограниченный fallback. HTTP 409 для сброшенной сессии и 410 для истёкшей требуют новой сессии. Квоты используют существующий код приложения `42901`: не полагайтесь только на HTTP-статус. Точные координаты, векторы и внутренние scores в этот контракт не входят.

Новые публикации ограничены **12 за скользящий час на пользователя**; мягкое удаление и повторы запросов не позволяют обойти лимит. Чтение рекомендаций — 60 RPC/минуту, действия — 120/минуту, телеметрия — 30 пачек/минуту, настройки — 30 запросов/минуту. Все квоты находятся на сервере, независимо от клиента.

Очереди обслуживаются в цикле: интерактивный профиль → новые публикации → интерактивный профиль → плановая подготовка → backfill. Пустые очереди пропускаются, занятая очередь не вытесняет остальные. Запросы пересчёта объединяются по пользователю и версии, обычный debounce — 1 секунда. Пулы до 200 постов готовятся только для активных пользователей из максимум 1200 кандидатов. Полный результат публикуется атомарно; уже открытая прокрутка сохраняет порядок. Текущие права перепроверяются на каждом чтении. Очистка и контроль очередей запускаются по отдельному расписанию.

Сервер проверяет принадлежность подтверждения, срок `delivery_expires_at`, версию текста/интересов и прошедшее время. Просроченные собственные события помечаются stale, не блокируя остальные корректные события пачки. Само сообщение клиента о видимости остаётся недоверенным сигналом; оно не доказывает внимание человека.

## Комментарии, репосты и жалобы

Все новые операции вызываются через `supabase.rpc`, с текущей Auth-сессией. Полный типизированный контракт и имена параметров — в `api/supabase.openapi.yaml`.

- `create_feed_comment`, `edit_feed_comment`, `delete_feed_comment`: до **200 символов**, автор редактирует собственный текст с проверкой версии. Удаление оставляет заглушку и ответы. `requested_reply_to` указывает корневой комментарий или любой ответ в той же ветке; ответы остаются плоскими. Имя адресата приходит в `reply_to`, не добавляется сервером в текст.
- `get_feed_comments`: корни с сортировкой `popular` (по умолчанию), `old`, `new`. `get_feed_comment_replies`: ответы по времени, от старых. До 30 элементов за RPC, курсор действует 20 минут и связан с читателем, постом, веткой, сортировкой и размером страницы. Повтор страницы сохраняет её ID; ещё не выданные корни сортируются по текущей популярности без повторов. Новые комментарии требуют новой сессии. Это не полный снимок рейтинга всей дискуссии.
- `set_feed_comment_liked`: передавайте `action_version`, `version` комментария и `post_version` как три соответствующих `expected_*` параметра. При конфликте обновите состояние перед новым намерением. При сетевом повторе сохраняйте исходный UUID и тело.
- `create_feed_repost`: пустой текст создаёт ссылочный репост, без дублирования поста и эмбеддинга. Непустой текст создаёт цитату: эмбеддинг собственного текста плюс доступный сейчас оригинал. Собственные фото цитат пока не предусмотрены. Цепочка ссылок ограничена четырьмя переходами. `delete_feed_repost` отменяет репост; `post.my_repost` возвращает ID/версию собственного обычного репоста.
- `get_friends_feed`: все текущие взаимные друзья **и авторы подписок**, их доступные посты, цитаты и обычные репосты, без дубликатов оригинала. Курсор с тем же протоколом страниц; сброс интересов инвалидирует его. Показы и действия отправляются через общие `record_feed_events` / `apply_feed_action`.
- `submit_feed_content_report`: `post` или `comment`, причина `spam/scam/pornography/other`. Жалоба попадает в существующую закрытую `private.moderation_user_reports` со снимком содержимого и скрывает цель для отправителя. Автоматического глобального бана нет. Лимиты раздельные: 20 жалоб на посты и 30 на комментарии в сутки, по 5 в минуту для каждого вида, повтор на ту же цель через семь дней. Старые жалобы на пользователя сохраняют свой отдельный лимит.

Обычные посты, цитаты и ссылочные репосты делят **12 созданий в час**. Комментарии — 30 новых в минуту и 500 в сутки. Для чтения комментариев и друзей — отдельные квоты по 60 RPC/минуту. Серверные счётчики повторных запросов ограничивают также идемпотентные повторы.

Комментарии, лайки комментариев и репосты добавляют ограниченные сигналы интереса к семантике соответствующего поста. Отмены убирают сигнал, сброс интересов отделяет старую эпоху. Текст комментариев отдельно не векторизуется; жалоба на комментарий не обучает отрицательный интерес к теме поста. Go-персонализатор использует существующую очередь объединённых пересчётов, а не синхронный вызов модели при каждом RPC.

На каждом чтении перепроверяются бан, блокировки, аудитория и вся цепочка оригиналов. Клиент должен уметь показывать заглушки комментариев с `text=null` и `author=null`; кэш не заменяет проверку серверного доступа. Новые таблицы закрыты RLS и не доступны клиенту или workers напрямую. Для модерации доступны `moderation_status` у постов/комментариев и существующая таблица глобальных банов.

## Подписки

Подписка и дружба — разные независимые связи. Можно иметь обе. Подписка не раскрывает координаты подписчика/автора и не открывает посты «только друзьям». Доступ к точному гео по-прежнему определяется существующим разрешением для текущих друзей.

- `get_feed_author_follow_state(author)` возвращает `following`, `version`, `can_follow`, `is_friend`. Та же связь приходит в `post.author_relationship`, чтобы клиенту не требовался отдельный запрос для каждой кнопки.
- `set_feed_author_followed` принимает желаемое состояние, UUID намерения и ожидаемую `version`. Сетевой повтор сохраняет исходный UUID/тело; новая подписка/отписка получает новый UUID и текущую версию. Старый повтор не отменяет новую отписку. При 409 нужно сверить состояние; устаревший ответ не заменяет более новую версию в кэше.
- `get_feed_following` и `get_feed_followers` доступны всем авторизованным активным пользователям. `requested_user` по умолчанию равен текущему пользователю. Списки перепроверяют блокировки, баны и удаление владельца/элементов; возвращают только ID/username/display_name и отношение вызывающего пользователя. Пагинация по UUID, до 100 элементов (по умолчанию 30), `has_more`/`next_cursor`; общий неограниченный подсчёт не выполняется.
- Посты друзей и подписок читаются через прежний `get_friends_feed`. Дружба+подписка не дублируют пост; отписка сохраняет независимую дружбу. Проверки аудитории и оригиналов работают и на повторе страницы. Блокировка снимает подписки в обе стороны и увеличивает версии; снятие блока их не восстанавливает.

Квоты разделены: запись — **120 запросов/мин, 2000/сутки**; новые активные подписки дополнительно **30/мин, 500/сутки**; чтение состояния — **120/мин**; список подписок — **60/мин**; список подписчиков — отдельные **60/мин**. Предел активных подписок — 10 000. Суточные счётчики используют UTC. Для квот сохраняется код приложения `42901`, который не следует определять только по HTTP-статусу. Все проверки выполняет Supabase, независимо от клиента.

Подписка немедленно объединяет запрос обновления рекомендаций. Действующая связь добавляет авторский источник и признак social, в том числе для фото без текста. Для семантики профиль подписчика получает ограниченную выборку доступных текстов: до двух постов от каждого из 100 последних доступных авторов подписок, затем применяется общий бюджет evidence. Семантический интерес может помочь найти других авторов той же темы. Эмбеддинги текстов автора не переписываются. Отписка убирает этот источник интереса при асинхронном пересчёте; самостоятельные лайки/чтение сохраняются.

Сброс интересов сохраняет явные подписки: они снова используются как текущий явный интерес, в отличие от очищаемой истории изученного поведения. Скрытие автора из рекомендаций и блокировки продолжают действовать поверх источника подписок. Новых клиентских обращений к Go нет.

`-Race` включает детектор гонок Go и требует настроенного C-компилятора. Для сквозных тестов остановите обычные workers и освободите очереди: тесты создают и удаляют собственные синтетические фикстуры. `-WithModel` проверяет отдельный процесс worker и настоящую E5. Индексационный нагрузочный участок использует технический encoder; чтения ленты измеряются через SQL RPC без HTTP/Auth. `-WithMedia -WithLoad` отдельно проверяет настоящие загрузки и подготовку 12 фото по 12 МП одновременно с 500 SQL-чтениями.

Медиа-регрессия также проверяет отказ TCP-соединений перед подтверждением результата в БД, настоящее истечение двухминутного lease и восстановление другой идентичностью. Отдельная инъекция потери ответа после успешного commit проверяет, что повторный failure/retry не отменяет уже готовое фото. Этот участок занимает около двух реальных минут и не останавливает общую PostgreSQL.

`-WithSoak -WithModel` работает только на локальной Supabase: 128 авторов и 16 читателей, JPEG/PNG до 20 МП, обычный поток и всплеск, около 500 HTTP-чтений ленты в минуту, действия и настоящий рекомендательный worker/E5. Сценарий завершает/перезапускает только собственные медиа-процессы, временно возвращает им Storage 503 через loopback-прокси и разрывает соединения ограниченного локального медиа-логина. Для часового запуска дополнительно проверяется настоящее истечение резерва. Принятые фото сверяются с прикреплёнными, публикации повторяются с теми же UUID, счётчики сверяются с очередями. Ограничения — 2 ГиБ исходящих оригиналов/живых объектов и минимум 4 ГиБ свободного места на системном и рабочем дисках. Логи, RSS/CPU процессов, агрегаты и итоги остаются в игнорируемой `.local/media-soak-*`; короткий прогон не помечается часовым.

## Асинхронная подготовка и версии

При обновлении до этого контракта остановите старый recommendation worker, примените обе новые миграции в основной истории YapChat, затем запустите обновлённые Go и Python процессы. Готовые страницы продолжают читаться во время остановки. Worker проверяет контракт при старте; несовместимый процесс не пишет результаты. Для удалённой Supabase миграции и выделенная роль готовятся отдельно; автоматического применения нет.

Индексация обрабатывает до 4 текстов за вызов `/embed-batch` по умолчанию (`-BatchSize 1..8`). Python выполняет один ограниченный ONNX-вызов одновременно; одно общее LRU-хранилище в памяти содержит до 2048 текстовых векторов. Модельные вызовы выполняются вне SQL-транзакций. При отказе модели задания получают backoff и сохраняются; новая публикация не теряется. Backfill вводится отдельными диапазонами и не понижает приоритет существующих live-заданий.

У задачи срок выполнения 25 секунд, lease — 60 секунд. Общий пул SQL равен concurrency + 2 (по умолчанию 4, максимум 10 соединений на процесс). Количество процессов также входит в общий бюджет подключений Supabase. Каждые 30 секунд worker пишет только агрегаты очереди и задержки публикаций; пользовательские тексты, UUID и секреты туда не включаются. Очистка идёт раз в минуту независимо от занятости очереди.

Пул и его delivery хранят независимые версии: `personalized-v2`, признаки `feed-features-v2`, политика `hybrid-v2`, полное имя embedding space. RPC возвращает `versions`; историческая сессия сохраняет фактические версии. Устаревший lease, epoch, версия текста или контракт модели не могут заменить актуальный результат. Готовый snapshot становится текущим только после завершения записи всей транзакции.

Для знакомства с новыми авторами используется подтверждённое покрытие автора: квалифицированные показы и число разных читателей по всем его постам. Новая публикация известного автора не обнуляет это покрытие. Собственные просмотры, доставка без просмотра, повторы event UUID и повторные показы одного поста одному читателю за сутки счётчик не увеличивают. При установке агрегат строится по ещё сохранённой истории показов, затем накапливается; удаление читателя убирает связь с его личностью, но не вычитает историческое покрытие. Это сигнал исследования авторов, а не оценка качества контента.

## Лента «Рядом»

`supabase.rpc('get_nearby_feed', ...)` принимает `requested_session`, `after_position`, `requested_limit` (1..30, по умолчанию 20), `requested_radius_km` (1..50, по умолчанию 50). Для первой страницы session=null, after_position=-1. Дальше передавайте выданный `next_cursor` с теми же размером страницы и радиусом.

Нужна собственная геопозиция, обновлённая не более 12 часов назад. Иначе сервер отвечает 412 `nearby_location_required`. В результат попадают только публикации с осознанно прикреплённой геометкой за 7 дней, в обратном хронологическом порядке. Собственный центр поиска сохраняется приватно на 20 минут; он не возвращается в ответе. Геоданные поста раскрываются по существующим разрешениям точной геолокации, подписка таких разрешений не даёт.

На запрос проверяется максимум 2000 пространственных кандидатов. Поэтому возможны `items=[]` и `has_more=true`: клиент должен продолжать по следующему курсору. Курсор продвигается через недоступные записи, не пропуская старые доступные посты. Повтор страницы сохраняет ID и снова проверяет права, оригиналы, удаления и баны. Отдельная квота — 60 чтений в минуту; сброс интересов инвалидирует сессию. ML для этой вкладки не требуется; её действия входят в общий профиль. В «Для вас» география остаётся небольшим источником кандидатов и слабым признаком.

Миграция `20261105221243_optimize_bounded_feed_reads.sql` прекращает обход после набора страницы и одного следующего доступного элемента. Внутри одного RPC переиспользуются только отрицательные решения для пары автор/аудитория; недоступный оригинал или жалоба на один пост не скрывают остальные публикации автора. Разрешённые элементы всегда проходят полную проверку. Протокол курсора и ограничение 2000 сохраняются.

## Измерение времени чтения ленты

```powershell
# Локальная Supabase, технический корпус: 60 читателей, 96 авторов,
# 2000 постов с векторами и 2000 постов фоновой очереди.
./scripts/benchmark-feed-local.ps1 -AppRoot $appRoot -Mode off -Label control
./scripts/benchmark-feed-local.ps1 -AppRoot $appRoot -Mode worker -Label control
# При запущенной настоящей E5:
./scripts/benchmark-feed-local.ps1 -AppRoot $appRoot -Mode inference -Label control
# Отдельная проверка роста нагрузки:
./scripts/benchmark-feed-local.ps1 -AppRoot $appRoot -Mode inference -RequestsPerMinute 1500 -Label growth
```

Перед сравнением остановите другие локальные recommendation workers: тест проверяет отсутствие подключений этой роли до начала. `off` не запускает worker; `worker` запускает настоящий Go-процесс с подставным inference для отделения SQL/блокировок от CPU модели; `inference` использует настоящую E5 с уникальными текстами каждого прогона. Начальные векторы технического корпуса не являются проверкой качества рекомендаций. Скрипт использует только локальный Supabase и ограниченную идентичность worker; тестовые пользователи и процесс удаляются при завершении.

По умолчанию — 60 секунд и 500 HTTP-запросов/мин, максимум 16 одновременно исполняемых запросов, ограниченная очередь генератора. Можно задать 500..3000 запросов/мин, 10..180 секунд и `-PageSize 1..30` (по умолчанию 10). Каждый читатель посещает все три вкладки. Проверяются первая/следующая/повторная страницы, отсутствие дублей и стабильность ID/подтверждений. Метрики холодного fallback собираются отдельно до запуска worker.

JSON под `.local/feed-perf-*.json` содержит p50/p95/p99/max по RPC и типу страницы, HTTP-статусы/код квоты/transport timeouts, ожидание генератора, полное время от планового прихода, достигнутую частоту, выборочные ожидания блокировок и продвижение backfill. Минимальный профиль проверяет p95<=300 мс/p99<=800 мс по каждой вкладке; верхние профили показывают пределы и отдельный `http_latency_budget_met`. Общий PASS верхнего профиля не означает соблюдения бюджета задержек. Короткий p99 не является доказательством длительного SLA.

Чтение готового «Для вас», фоновые pgvector-запросы и inference — разные измерения. Их нельзя объединять в одну оценку стоимости векторного поиска. Runtime-диагностика worker дополнительно содержит агрегаты ограниченного SQL-пула: число соединений, отменённые захваты и накопленное время ожидания свободного соединения. Это не время исполнения SQL; начальное создание соединений также может входить в ожидание.

Для редких длинных хвостов теста `TestSupabaseLocalPreparationLoad` можно временно задать `YAP_FEED_TRACE=1`. Тогда тест записывает фазы медленных HTTP-запросов, классы/ожидания активных SQL и агрегаты heap/GC клиентского процесса. Тексты SQL, JWT и параметры запросов не выводятся. Фоновый сбор сначала материализует ограниченные ID кандидатов; сборка страниц «Друзья»/«Рядом» сначала ограничивает текущую страницу, а «Для вас» обходит ограниченный резерв последовательно. Проверки доступа выполняются по этим наборам, сохраняя полный контроль оригиналов. `TestSupabaseLocalFeedWorkBound` дополнительно проверяет число дорогих вызовов при принудительно невыгодных локальных планах; настройки действуют только внутри откатываемой тестовой транзакции.

## История обратной связи и будущие обучающие данные

Каноническая миграция `20261105235213_feed_feedback_history.sql` добавляет закрытый журнал `recsys.feedback_facts` версии1. Проверенные RPC сохраняют переход состояния и факт в одной транзакции. Повторы request UUID не дублируются; принятый no-op лайка/подписки сохраняет новую версию состояния. Журнал не является новым клиентским API: RLS включена, чтение/запись закрыты для anon, authenticated и runtime workers. Существующие проверки и rate limits остаются в RPC.

Факт содержит серверные event UUID/sequence/time/transaction, пользователя/epoch, тип и ID цели, версии поста/комментария/действия, original/root/reply, состояние и доступный delivery-контекст. Где RPC не принимает delivery, источник остаётся `unattributed`: показ не придумывается. Сырой текст, фото, координаты и причины жалоб в журнал не копируются. При подтверждении внимания сохраняются фактические версии producing snapshot и числовые признаки; отсутствующие версии не заменяются константой экспортера. `recorded_at` — время записи внутри серверной транзакции, а не обещание времени её commit; доступность обучающей метки должен контролировать отдельный экспорт.

| Сигнал | Семантика исхода |
|---|---|
| Impression / dwell / open | Только подтверждённая видимость. Cumulative dwell берётся максимумом; повтор без прогресса не увеличивает журнал. Собственные показы исключены из обучения и счётчика показов поста. |
| Like / unlike | Итоговое версионированное состояние; unlike снимает положительный сигнал и не означает неприязнь к теме. |
| Комментарий / ответ / лайк комментария | Отдельная цель обсуждения, с версиями и отменой; одобрение текста поста из этого не выводится. |
| Репост / цитата / отмена | Отдельные сущности и состояния. Оригинал и собственная подпись не считаются двумя одинаковыми действиями. |
| Follow / unfollow | Явный интерес к автору, независимо от дружбы; не положительная метка всех постов автора. |
| Меньше похожего / отмена | Отдельный отрицательный семантический сигнал и его отмена. |
| Жалоба | Цели post/comment/user различаются; жалоба на комментарий или пользователя не становится отрицательной меткой поста. |
| Скрытие / блок / бан | Настройки и жёсткие проверки Supabase; модель их не заменяет. Внешнее «поделиться» пока не поддерживается как отдельный сигнал. |

`ml/feedback.py` — чистое восстановление независимых outcomes и known/unknown masks. Требуется подтверждённый показ и созревшее окно. Учитываются отмены, epoch/reset, серверный порядок/версии, изменения контента и дедупликация показов за UTC-день; внимание в повторных подтверждённых deliveries объединяется максимумом. Предсуществующий лайк/подписка является состоянием, а не доказательством причинного эффекта показа. Общей суммы «одобрения» и новых serving-весов этот модуль не вводит.

История начинается с `feedback_history_contract.started_at`; прошлые переходы не восстанавливаются из изменяемых таблиц. Retention — 30 дней, очистка ограниченными `SKIP LOCKED` пачками через существующую maintenance-функцию; удаление аккаунта удаляет его факты. Экспорт должен использовать границу покрытия не раньше max(started_at, текущий retention floor). `source` означает серверную таблицу, а не происхождение данных от реальных людей: synthetic/curated/pilot различаются отдельно в dataset manifest.

```powershell
.venv/Scripts/python.exe -m unittest discover -s ml -p test_feedback.py -v
./scripts/test-supabase-local.ps1 -AppRoot $appRoot -Race -Run '^TestSupabaseLocalFeedback$'
./scripts/test-supabase-local.ps1 -AppRoot $appRoot -Race -WithLoad -Run '^TestSupabaseLocalFeedbackLoad$'
```

Миграция `20261106143352_optimize_followed_author_reads.sql` добавляет покрывающий индекс метаданных активных постов по автору. Кандидаты читаются без полного содержимого поста; полные строки нужны для проверки цитат и выбранной страницы. Исключения текущей сессии читаются один раз, лишнее соединение кандидатов со всей таблицей удалено. Сборка сначала фиксирует записи текущей страницы, затем загружает только их посты через зависимый поиск по ID. Эти изменения устраняют найденные при регрессии повторные обходы общего индекса и квадратичные соединения при устаревшем плане. SQL-контракт `feed_follow_author_work_bound.sql` прогревает план, увеличивает чужие страницы и проверяет реальное число прочитанных строк; `TestSupabaseLocalFollowAuthorWork` запускает тот же канонический тест из `AppRoot`. В `FollowsLoad` p95<=300мс/p99<=800мс проверяются отдельно для каждого RPC, дополнительно к пропускной способности. Права и порядок ленты сохранены.

`ml/export.py` остаётся изолированным прототипом для старой тестовой базы. Экспорт рабочего журнала и временное разделение описаны ниже. Обучаемый ranker пока не включён.

## Сравнение текстовых моделей

Используйте один собранный корпус и запускайте варианты отдельными процессами с одинаковым числом потоков CPU. `--download` скачивает публичные веса зафиксированных ревизий. Сначала проверьте `--smoke`, особенно для BGE-M3 FP32 (около 2,3 ГБ весов на диске).

```powershell
$corpus = '.local/output/quality-corpus'
# Можно собрать тот же текстовый срез без скачивания фото:
# python ml/quality_corpus.py --text-only $corpus
$env:HF_HOME = (Join-Path (Get-Location) '.cache/huggingface')
python ml/benchmark_text.py --model bge-m3 --corpus $corpus --output .local/bge-smoke.json --smoke --download
python ml/benchmark_text.py --model e5-int8 --corpus $corpus --output .local/e5-int8.json --download
python ml/benchmark_text.py --model e5-fp32 --corpus $corpus --output .local/e5-fp32.json --baseline .local/e5-int8.json --download
python ml/benchmark_text.py --model bge-m3 --corpus $corpus --output .local/bge.json --baseline .local/e5-int8.json
```

Для точного и HNSW-поиска установите `ml/requirements-benchmark.txt` и добавьте `--pg`. Тест подключается к локальной Supabase на `127.0.0.1:54322` с паролем из `PGPASSWORD` и использует временную таблицу на одно соединение. `--pg-growth 10000` добавляет отдельный синтетический сценарий размера индекса. Полнота HNSW здесь считается относительно точного top‑K. Качество энкодера считается относительно авторских тематических меток. Задержка поиска измеряется от отправки SQL до получения ID.

JSON содержит контрольные суммы корпуса и артефактов, размерность, prefix, pooling, нормализацию, разрядность, метрики по языковым срезам, время CPU и пиковую рабочую память процесса. Если по результатам следующего эксперимента меняется модель, храните новые векторы в отдельном пространстве. Сначала заполните его в фоне с ограниченной скоростью, затем пересчитайте интересы и пулы в новом пространстве. Переключайте новые сессии только после проверки полноты и качества новых снимков. Старые снимки и векторы нужны для существующих сессий и отката.
