# Yap Algorithm

Внутренний рекомендательный сервис YapChat: Go, PostgreSQL/pgvector и локальная CPU-модель multilingual E5. Проект находится в разработке.

## Текущий статус

| Контур | Что работает |
|---|---|
| Настоящая Supabase YapChat | Текст и фото, закрытый Storage и подготовка медиа, геометки, лайки/отмены, показы/чтение, профили интересов и персональные страницы через Supabase |
| Изолированный прототип | Несколько источников кандидатов, профили интересов из взаимодействий, гибридное ранжирование, разнообразие, тестовый симулятор и исследовательское обучение |

Основной цикл персонализации и жизненный цикл фото перенесены в локальную Supabase. Отдельные выдачи «друзья/рядом», подписки, репосты, комментарии, интеграция жалоб и обучение ranker добавляются следующими этапами. Облачное развёртывание пока не проверялось.

Клиент обращается к Supabase Auth/RPC и Storage. Внутренний `cmd/worker` забирает задания из той же PostgreSQL, вызывает модель и записывает производные векторы обратно. Клиентский HTTP API для этого worker отсутствует. Шлюзом и источником истины остаётся Supabase.

## Архитектура

- `internal/domain` — ограничения предметной области, векторы и ошибки.
- `internal/application` — сценарии обработки и интерфейсы зависимостей.
- `internal/adapters/postgres` — закрытый SQL-контракт, пул и проверка прав.
- `internal/model` — HTTP-адаптер модели с проверкой пространства эмбеддингов.
- `internal/ranking` — признаки, базовый score и разнообразие.
- `cmd/worker` — сборка зависимостей, параллельность, остановка и очистка.
- `cmd/media-worker`, `internal/adapters/photo`, `internal/adapters/storage` — отдельная ограниченная обработка изображений и физическая очистка через Storage API.
- `internal/api`, `internal/store`, `internal/worker`, `cmd/yap-algorithm` — сохраняемый изолированный прототип.

Публикация и задание записываются одной транзакцией. Работники используют `SKIP LOCKED`, ограниченный срок владения и повторные попытки. Перед сохранением вектора повторно проверяются версия и состояние поста. Сервисная роль имеет права только на внутренние функции, а не на изменение публикаций или профилей.

Для ранжирования используются архитектурные идеи поэтапного конвейера [x-algorithm](https://github.com/xai-org/x-algorithm): поиск кандидатов, фильтрация, оценка, разнообразие и итоговые проверки доступа. Собственные модели и веса X здесь не используются. Текущий гибридный score — проверяемая исходная модель; его коэффициенты ещё требуют продуктовой валидации.

## Зависимости и модель

Нужны Go 1.27.3+, Python 3.12 и Docker для локальных проверок. Минимальная Go закреплена с учётом исправлений стандартной библиотеки; при включённом автоматическом выборе toolchain нужная версия скачивается в локальный кэш проекта. Зависимости закреплены в `go.mod`, `go.sum` и `ml/requirements.lock`. Масштабирование изображений использует официальную `golang.org/x/image` v0.47.0.

```powershell
uv venv --python 3.12 .venv
uv pip sync --python .venv/Scripts/python.exe ml/requirements.lock
```

Используется `intfloat/multilingual-e5-small`, ревизия `614241f622f53c4eeff9890bdc4f31cfecc418b3`, ONNX int8, 384 измерения. При первом запуске скачиваются открытые веса; они не включены в репозиторий. GPU и платный модельный API не требуются.

## Локальная Supabase YapChat

Нужна работающая локальная Supabase основного приложения на портах API 54321 / PostgreSQL 54322 с каноническими миграциями `20261104195702_feed_recommendation_pipeline.sql`, `20261104213317_personalized_feed.sql` и `20261104225631_feed_media_pipeline.sql` из репозитория YapChat. Они зависят от существующих проверок и таблиц приложения. Worker не применяет миграции при запуске.

```powershell
$appRoot = 'D:/path/to/Yap_chat'
./scripts/supabase-local.ps1 -Action setup -AppRoot $appRoot
```

Настройка создаёт ограниченный локальный логин и случайный пароль. Настройки остаются в игнорируемом `.local/`. Ключ Supabase `service_role` самому worker не нужен.

В отдельных терминалах:

```powershell
./scripts/local.ps1 -Action model
# После сообщения ready, в другом терминале:
./scripts/supabase-local.ps1 -Action worker
# Обработать доступную очередь и завершиться:
./scripts/supabase-local.ps1 -Action worker -Once
# После устранения ошибки модели можно переотправить исчерпавшие попытки:
./scripts/supabase-local.ps1 -Action worker -RetryFailed
```

По умолчанию работают 2 задачи с максимум 4 SQL-соединениями. Для удалённого запуска `cmd/worker` принимает `DATABASE_URL` и внутренний `MODEL_URL`; удалённая БД требует `sslmode=verify-full`. Локальные helper-скрипты удалённые адреса не принимают. Облачное развёртывание ещё не проверено.

### Фото и геометки

```powershell
./scripts/media-local.ps1 -Action setup -AppRoot $appRoot
./scripts/media-local.ps1 -Action worker
# Обработать доступные фото и удаления, затем завершиться:
./scripts/media-local.ps1 -Action worker -Once
```

Медиа использует отдельный логин БД и JWT с ролью `yap_feed_media_worker`, ограниченной Storage RLS. Ключ `service_role` и секрет подписи JWT обработчику не передаются. Локальный setup выдаёт токен на 7 дней; для продления повторите setup и перезапустите процесс. Конфигурация остаётся в `.local/`. Для удалённого запуска нужны `MEDIA_DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` и заранее выпущенный `MEDIA_STORAGE_TOKEN` этой роли. URL Storage требует HTTPS, БД — проверенного TLS. Выпуск и ротация удалённой идентичности требуют отдельной настройки окружения; локальный helper туда не подключается.

По умолчанию работает одна медиа-задача, максимум — две. Декодирование ограничено 20 мегапикселями и стороной 8192; качественное масштабирование требует отдельного бюджета памяти. На небольшом VPS начните с одной задачи и измерьте память на своём корпусе. Медиа не занимает очередь семантической индексации.

Порядок для будущего клиента через существующую Supabase-сессию:

1. `reserve_feed_photo(post_id, photo_id, bytes, MIME)` возвращает точный путь в закрытом `feed-uploads`. Сохраните UUID и исходные параметры для повторов.
2. Загрузите JPEG/PNG до 5 МиБ обычным `storage.from(bucket).upload(path, bytes, upsert: false)` с объявленным MIME. Оригинал нельзя читать, копировать, перемещать или подписывать.
3. Вызовите `confirm_feed_photo`, затем `get_feed_photo_status` с увеличивающимся интервалом опроса. До состояния `ready` публикация невозможна. Держите локальное превью; сервер проверяет декодирование, поворот EXIF и удаляет метаданные.
4. `publish_feed_post` принимает UUID черновика, текст, аудиторию, язык, упорядоченные UUID готовых фото и необязательную геометку. До трёх фото; текст может отсутствовать. Фото и геометка после публикации фиксированы, текст редактируется обычным RPC.
5. DTO поста содержит `photos` с путями очищенных JPEG и превью. Читайте через авторизованный Storage download с текущим JWT. Подписанные и публичные URL закрыты, текущие права проверяются на каждом сетевом чтении. Кэш байтов должен быть привязан к аккаунту и очищаться при потере доступа; уже скачанные байты сервер отозвать не может.

Есть `cancel_feed_draft` для отказа от загрузки. На пользователя разрешены четыре активных черновика, 48 новых резервирований за скользящий час, по 60 запросов/минуту на каждую медиа-операцию. Черновик истекает через час. Физическая очистка оригиналов, прерванных попыток и удалённых постов идёт через устойчивую очередь и Storage API; рабочий медиа-процесс должен быть запущен. После исправления сбоя `-RetryFailed` возвращает ограниченную пачку исчерпанных заданий в работу.

Геометка хранит место публикации и не зависит от видимости пользователя в поиске рядом. Точные координаты получает автор и текущие друзья с разрешением точной локации без индивидуального исключения. Остальным возвращается только `nearby=true` в пределах 50 км при собственной позиции не старше 12 часов; точного расстояния нет.

Фото без текста не отправляется в E5 и не получает выдуманный семантический вектор. Его лайки и чтение влияют на авторские/поведенческие источники. Мультимодальная семантика — отдельный будущий этап оценки моделей.

### Ручная проверка без клиента

Откройте локальную Studio на `http://127.0.0.1:54323`. Создайте отдельного тестового пользователя в Authentication и скопируйте его UUID. В SQL Editor выполните:

```sql
begin;
select set_config('request.jwt.claim.sub', 'UUID_ТЕСТОВОГО_ПОЛЬЗОВАТЕЛЯ', true);
set local role authenticated;
select public.create_feed_post(
  'f0000000-0000-4000-8000-000000000001',
  'Разрабатываю сервер на Go и PostgreSQL', 'public', 'ru'
);
commit;
```

Это локальная административная имитация идентичности, а не проверка JWT. Для настоящего Auth/PostgREST предусмотрен сквозной тест ниже. Не меняйте `auth.uid()` или claims в клиентском коде.

Пост сохраняется в `feed.posts`, задание — в `recsys.index_jobs`. После обработки проверьте в SQL Editor:

```sql
select p.id, p.version, j.attempts, j.done_at, j.last_error,
       e.post_version, e.model, extensions.vector_dims(e.embedding) as dimensions
from feed.posts p
left join recsys.index_jobs j on j.post_id = p.id
left join recsys.post_embeddings e on e.post_id = p.id
where p.id = 'f0000000-0000-4000-8000-000000000001';
```

Ожидается завершённое задание, отсутствие ошибки и вектор размерности 384 с текущей версией поста. Измените текст через `public.edit_feed_post(id, expected_version, new_text)` — версия увеличится, вектор будет пересчитан. Повтор создания с исходным UUID и параметрами не создаёт дубликат.

Для проверки персонализации создайте второго тестового пользователя и несколько постов о разных темах. Под его идентичностью вызовите `public.get_for_you_feed()`, возьмите `delivery_id` и `post.action_version` из ответа и вызовите:

```sql
select public.apply_feed_action(
  'НОВЫЙ_UUID_ДЕЙСТВИЯ', 'DELIVERY_ID_ИЗ_ВЫДАЧИ', 'like', 0
);
-- После обработки worker:
select public.get_for_you_feed();
```

Последний аргумент — фактический `action_version`, а не всегда 0. Для транспортного повтора сохраните исходный UUID и всё тело запроса. Новое намерение пользователя получает новый UUID и актуальную версию. Повтор старого запроса не отменяет более новое действие. На HTTP 409 сверяйте текущее состояние, не переигрывайте старое намерение с новой версией.

Текстовая `post.version` и `post.action_version` — разные версии. Для семантического сигнала `less_similar` используйте тот же RPC; для скрытия автора и сброса есть отдельные RPC.

## Контракт для клиента

[OpenAPI Supabase RPC](api/supabase.openapi.yaml) описывает параметры, ответы, пагинацию и ошибки. Все вызовы идут через существующую Supabase-сессию и сетевой слой приложения. Не обращайтесь к Go или закрытым таблицам из клиента.

- `get_for_you_feed` — до 30 постов, непрозрачный UUID сессии и `next_cursor`; передавайте оба поля курсора на следующей странице. Позиции могут иметь пропуски после банов, удаления или изменения текста.
- `apply_feed_action` — `like`, `unlike`, `less_similar`, `undo_less_similar`, с UUID намерения и версией состояния действий.
- `record_feed_events` — до 100 событий за запрос. Доставленный пост ещё не является показом: отправляйте impression после 1 секунды при видимости хотя бы 50%, затем cumulative dwell/open_post.
- `set_recommendation_author_hidden`, `reset_recommendation_interests` — идемпотентные операции настроек с UUID запроса. Выполняйте изменения настроек последовательно в клиентском репозитории.
- `get_recommendation_hidden_authors` — keyset-пагинация списка скрытых авторов.

Показы и действия с любой поверхности используют общий профиль. Сейчас `get_feed_post` выдаёт подтверждение поверхности `direct`, а персональная страница — `for_you`; будущие серверные выдачи друзей и географии будут использовать тот же механизм подтверждений.

`refresh.status` показывает `fresh/queued/retrying/failed`. При недоступности worker остаётся допустимая подготовленная выдача либо ограниченный fallback. HTTP 409 для сброшенной сессии и 410 для истёкшей требуют новой сессии. Квоты используют существующий код приложения `42901`: не полагайтесь только на HTTP-статус. Точные координаты, векторы и внутренние scores в этот контракт не входят.

Новые публикации ограничены **12 за скользящий час на пользователя**; мягкое удаление и повторы запросов не позволяют обойти лимит. Чтение рекомендаций — 60 RPC/минуту, действия — 120/минуту, телеметрия — 30 пачек/минуту, настройки — 30 запросов/минуту. Все квоты находятся на сервере, независимо от клиента.

Очереди индексации и персонализации обслуживаются по очереди, без вытеснения одной другой. Пулы до 200 постов готовятся только для активных пользователей, запросы пересчёта объединяются. Неизменившийся пул переиспользуется с исходным временем признаков; текущие права перепроверяются на каждом чтении. Очистка работает ограниченными автокоммитными пачками в отдельном временном бюджете.

Сервер проверяет принадлежность подтверждения, срок `delivery_expires_at`, версию текста/интересов и прошедшее время. Просроченные собственные события помечаются stale, не блокируя остальные корректные события пачки. Само сообщение клиента о видимости остаётся недоверенным сигналом; оно не доказывает внимание человека.

## Проверки

```powershell
go test ./...
go vet ./...
./scripts/test-supabase-local.ps1 -AppRoot $appRoot
# При готовой локальной модели:
./scripts/test-supabase-local.ps1 -AppRoot $appRoot -WithModel
# Вместе с настоящим Storage и отдельным медиа-процессом:
./scripts/test-supabase-local.ps1 -AppRoot $appRoot -WithModel -WithMedia -Race
# Дополнительно: очередь на 10 001 посте и параллельные SQL-чтения:
./scripts/test-supabase-local.ps1 -AppRoot $appRoot -WithModel -WithLoad
# Замер только нагрузки без накладных расходов race detector:
./scripts/test-supabase-local.ps1 -AppRoot $appRoot -WithLoad -Run '^TestSupabaseLocalPipeline$/^personalized_feed$/^500_active_users_load$'
```

Проверка известных уязвимостей: `go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...`. Минимальная Go в `go.mod` включает исправления HTTP/TLS; не отключайте автоматический выбор toolchain для сборки старой версией.

`-Race` включает детектор гонок Go и требует настроенного C-компилятора. Для сквозных тестов остановите обычные workers и освободите очереди: тесты создают и удаляют собственные синтетические фикстуры. `-WithModel` проверяет отдельный процесс worker и настоящую E5. Индексационный нагрузочный участок использует технический encoder; чтения ленты измеряются через SQL RPC без HTTP/Auth. `-WithMedia -WithLoad` отдельно проверяет настоящие загрузки и подготовку 12 фото по 12 МП одновременно с 500 SQL-чтениями.

## Изолированный рекомендательный прототип

Он работает отдельно от настоящей Supabase, на PostgreSQL 55432. Его тестовые миграции находятся в `tests/fixtures/migrations`: их нельзя переносить поверх основной базы приложения. Единственная каноническая история общей Supabase находится в `Yap_chat/supabase/migrations`.

```powershell
./scripts/local.ps1 -Action init
./scripts/local.ps1 -Action seed -Posts 1000
# В отдельных терминалах: model, worker, api
./scripts/local.ps1 -Action model
./scripts/local.ps1 -Action worker
./scripts/local.ps1 -Action api
# После запуска:
./scripts/local.ps1 -Action simulate -Rounds 3
./scripts/local.ps1 -Action test
```

HTTP-контракт прототипа находится в `api/openapi.yaml`, API доступен только для fixture-базы. Корпус и тестовые идентичности остаются в `.local/`. Обучение и сравнение методов исследовательские; синтетическая метрика не подтверждает качество рекомендаций для реальных людей.

Локальные отчёты, планы, граф знаний, корпуса, модельные артефакты и секреты исключены из публикации.
